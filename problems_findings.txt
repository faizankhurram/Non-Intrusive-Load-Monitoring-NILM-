This document consists of all the documented problems/limitations/obstacles that we encountered during the construction, testing and improvement of our project. Moreover, for each obstacle, we describe as to what it was, due to what it occurred and what thing we tried to implement, and the outcome of that new thing we tried (did it work, or not, and if not, where did we go next).

================================================================================

PROBLEM #1: NumPy version incompatibility with PyTorch
------------------------------------------------------
WHAT HAPPENED:
  Running `python run_pipeline.py` crashed with:
    RuntimeError: Numpy is not available
  and a warning: "A module that was compiled using NumPy 1.x cannot be run in
  NumPy 2.5.4"

DUE TO:
  PyTorch 2.2.0 (installed on the system) was built against NumPy 1.x. The
  project initially had numpy>=2.0 in requirements.txt, and pip had upgraded
  numpy to 2.5.4 which broke the torch <-> numpy C-level ABI. Tensor .numpy()
  calls failed entirely.

WHAT WE TRIED:
  Downgraded numpy to 1.26.4 (latest 1.x) and pandas to 2.3.3 (compatible
  with numpy 1.x). Pinned requirements.txt to "numpy>=1.26,<2.0" and
  "pandas>=2.0,<3.0".

OUTCOME:
  Fixed. torch.tensor.numpy() works correctly. Pipeline proceeds past the
  crash point.

PROBLEM #2: Extremely long training time (~5-6 hours estimated)
---------------------------------------------------------------
WHAT HAPPENED:
  The pipeline successfully loaded data (3.14M rows), created 1.83M training
  windows, and started MLP training for the first appliance (air1). Each epoch
  was taking very long due to the massive dataset size on CPU. Estimated total
  runtime for all 3 appliances x 2 models x 50 epochs was 5-6 hours.

DUE TO:
  - 6 homes produced ~1.83M overlapping training windows (step=1, every minute).
  - Batch size of 256 meant ~7,150 batches per epoch.
  - 50 max epochs with patience of 7 = many epochs before early stop.
  - LSTM with 2 layers is slow on CPU.
  - All of this multiplied by 3 appliances x 2 models = 6 full training runs.

WHAT WE TRIED:
  Multiple config changes to reduce total computation:
  1. Reduced homes from 6 to 5 (minimum required by CCP).
  2. Added WINDOW_STEP=5 (sample every 5th window instead of every overlapping
     minute) — cuts training windows by ~5x, from ~1.83M to ~300K.
  3. Increased BATCH_SIZE from 256 to 1024 (fewer optimizer steps per epoch).
  4. Reduced EPOCHS from 50 to 20.
  5. Reduced PATIENCE from 7 to 4 (earlier stopping).
  6. Reduced LSTM_LAYERS from 2 to 1 (faster LSTM forward pass).
  Cleared cached data so the pipeline regenerates with new settings.

OUTCOME:
  Confirmed working — training windows dropped from ~1.83M to ~366K. Epochs
  capped at 20. Pipeline reached evaluation stage successfully.

PROBLEM #3: JSON serialization crash on numpy float32
-----------------------------------------------------
WHAT HAPPENED:
  After MLP training and evaluation for air1 completed, the pipeline crashed at
  json.dump() with:
    TypeError: Object of type float32 is not JSON serializable

DUE TO:
  sklearn metrics (accuracy_score, etc.) return numpy float32 values. Python's
  round() preserves the numpy dtype, so round(acc, 4) returns a numpy.float32
  which json.dump cannot serialize natively.

WHAT WE TRIED:
  Wrapped every metric value with float() in evaluate.py to cast numpy scalars
  to native Python floats before JSON serialization.

OUTCOME:
  Fixed. Metrics now serialize correctly to JSON.

PROBLEM #4: Pipeline too long to complete in one sitting
--------------------------------------------------------
WHAT HAPPENED:
  Even after the speedup changes (Problem #2), a full pipeline run still takes
  a significant amount of time on CPU (6 training runs total: 3 appliances x
  2 models). The laptop could not stay powered long enough to finish, and there
  was no way to pause and resume — a crash or shutdown meant restarting from
  scratch.

DUE TO:
  The original pipeline had no checkpointing or resume capability. Every run
  started fresh: re-loading data, re-creating windows, re-training all models
  even if some had already completed.

WHAT WE TRIED:
  Implemented full pause/resume support across two files:

  1. training.py — Added:
     - Signal handler (Ctrl+C) that sets a flag to stop after current epoch
     - save_checkpoint() / load_checkpoint() to persist model state, optimizer
       state, epoch number, best val loss, patience counter, and history
     - On resume, training continues from the saved epoch
     - Checkpoint files are deleted once training completes normally

  2. run_pipeline.py — Added:
     - Skips data preparation (steps 1-5) if windowed .npz files already exist
     - Skips any model whose metrics JSON + .pt file already exist
     - Detects checkpoint files to resume interrupted training
     - Catches KeyboardInterrupt and exits cleanly

  How to use:
  - Run: python run_pipeline.py
  - To pause: press Ctrl+C once (waits for current epoch to finish, saves checkpoint)
  - To resume: python run_pipeline.py (automatically picks up where it stopped)

OUTCOME:
  Implemented successfully. The pipeline can now survive power loss, user
  interruption, or crash and resume without re-doing completed work.

FIRST COMPLETE RUN — RESULTS ANALYSIS
--------------------------------------
Results from the first pipeline run (all 6 models trained):

  Model  Appliance       Acc    BalAcc  MacF1   MAE(W)  RMSE(W)
  MLP    air1           0.7413  0.8213  0.4309  396.87  787.67
  LSTM   air1           0.7924  0.8521  0.4487  393.80  856.75
  MLP    refrigerator1  0.5987  0.5000  0.3745   66.64   79.82
  LSTM   refrigerator1  0.5987  0.5000  0.3745   67.74   80.78
  MLP    dishwasher1    0.4487  0.5193  0.3853   29.02   88.30
  LSTM   dishwasher1    0.4536  0.5219  0.3963   30.54   98.06

NONE of the appliances met the minimum benchmarks (Acc>=85%, BalAcc>=75%,
MacF1>=0.70). Root cause analysis:

  1. UNSEEN HOME DISTRIBUTION SHIFT: Home 4031 (reserved entirely for test)
     had vastly different appliance usage patterns than the training homes.
     - air1 test: only 284 ON out of 183,492 (0.15%) vs 25.7% in train
     - dishwasher1 test: 58.6% ON vs 2.7% in train
     This made the test set unrepresentative.

  2. REFRIGERATOR PREDICTS ALL-ON: Both models predicted every sample as ON.
     Confusion matrix: [[0, 73634], [0, 109858]]. Balanced accuracy = 0.50.
     The model failed to learn the fridge's cycling pattern from aggregate.

  3. LOW THRESHOLDS: The 10th-percentile threshold method produced values
     (air1=100W, fridge=50W, dishwasher=10W) that were too low, labeling
     noise/standby as ON and creating noisy labels.

  4. LOSS FUNCTION: Standard weighted BCE wasn't sufficient for the severe
     class imbalance. The model converged to predicting the majority class.

  5. NO BATCHNORM: The MLP had no normalization layers, leading to unstable
     gradients and poor convergence.

CONCLUSIONS:
  - The unseen-home test strategy is too aggressive for a first run
  - Thresholds need domain-knowledge tuning, not purely statistical
  - Need focal loss or similar to handle extreme imbalance
  - Models need BatchNorm/LayerNorm for training stability

IMPROVEMENT ROUND #1 — Changes Implemented
-------------------------------------------

  1. SPLITTING STRATEGY: Removed the unseen-home holdout. Now ALL homes
     contribute 70/15/15 chronologically to train/val/test. This ensures
     the test set has representative appliance distributions.

  2. ON/OFF THRESHOLDS (labeling.py): Replaced the statistical percentile
     method with fixed domain-knowledge thresholds:
       - air1: 200W (HVAC compressor clearly above this)
       - refrigerator1: 30W (compressor cycling above standby)
       - dishwasher1: 20W (any active cycle phase)
     These are validated against training data distributions.

  3. FOCAL LOSS (training.py): Replaced weighted BCE with Focal Loss
     (gamma=2.0). Focal loss down-weights easy/well-classified samples
     and focuses learning on hard, misclassified ones. This directly
     addresses the class imbalance problem where the model just learned
     to predict the majority class.

  4. BATCHNORM IN MLP (mlp.py): Added BatchNorm1d after each linear
     layer in the backbone. Also added a deeper classification head
     (Linear->ReLU->Linear->Sigmoid) instead of single-layer.

  5. LAYERNORM IN LSTM (lstm_model.py): Added LayerNorm on the last
     hidden state before the heads. This stabilizes the LSTM output.

  6. LR SCHEDULING (training.py): Added cosine annealing with 2-epoch
     linear warmup. Warmup prevents unstable early gradients; cosine
     annealing lets the model fine-tune in later epochs with a lower LR.

  7. GRADIENT CLIPPING (training.py): Added max_norm=1.0 gradient clipping
     to prevent exploding gradients, especially important for LSTM.

  8. WEIGHT DECAY (training.py): Added L2 regularization (1e-5) to the
     Adam optimizer to reduce overfitting.

  9. DEEPER HEADS: Both MLP and LSTM now have 2-layer heads
     (Linear(hidden,32)->ReLU->Linear(32,1)) for both classification
     and regression, giving more capacity to map features to outputs.

OUTCOME:
  Completed — ran fresh pipeline, results analyzed in next section.

Results from the second pipeline run:

  Model  Appliance       Acc    BalAcc  MacF1   MAE(W)  RMSE(W)
  MLP    air1           0.8192  0.8722  0.4650  246.01  497.96
  LSTM   air1           0.8967  0.8846  0.4968  172.72  461.83
  MLP    refrigerator1  0.6747  0.6648  0.6532   56.00   72.11
  LSTM   refrigerator1  0.7445  0.6489  0.6575   52.21   70.60
  MLP    dishwasher1    0.1970  0.5013  0.1688   30.92  117.82
  LSTM   dishwasher1    0.2491  0.5244  0.2376   30.53  117.29

Comparison vs Run 1:
  - air1: HUGE improvement. LSTM Acc 0.79->0.90, BalAcc 0.85->0.88.
    However Macro-F1 still only 0.50 because ON class has only 282
    samples in test (0.3%). The model catches 246/282 ON (87% recall)
    but precision is 246/(246+9688) = 2.5%, killing F1.
    Power MAE improved from 394->173W.

  - refrigerator1: Major fix. From predicting ALL-ON (F1=0.37) to
    actual discrimination (F1=0.66). LSTM Acc 0.60->0.74.
    Confusion: [[11323,20256],[3797,58774]] — ON recall 94%, OFF 36%.
    Still biased toward ON but much better than before.

  - dishwasher1: GOT WORSE. MLP Acc 0.45->0.20. Confusion shows model
    predicts almost everything as ON: [[594,75505],[94,17957]].
    The focal loss with pos_weight=8.59 was too aggressive, causing
    model collapse to all-ON prediction.

ROOT CAUSE ANALYSIS of remaining failures:

  1. DISHWASHER: Fundamentally problematic appliance. Power distribution:
     43% zero, 37% at 1-10W (standby), only 2% above 50W. The actual
     ON-cycle power is very weak and rare. A 20W threshold labels mostly
     standby noise as "ON", creating unreliable labels. No model can
     learn from noisy labels with a tiny true-ON percentage.

  2. AIR1 MACRO-F1: The metric is dragged down by the ON class having
     ultra-low precision (2.5%) despite high recall (87%). With only
     282 ON samples in 94K test, even 9K false positives destroy F1.
     The threshold of 200W may be too low — many readings in 200-500W
     range could be partial-cycle noise.

  3. REFRIGERATOR OFF-RECALL: The model over-predicts ON (64% of true-
     OFF samples predicted as ON). The 30W threshold sits in a noisy
     transition zone between standby (1-50W) and compressor (50-200W).

  4. POS_WEIGHT TOO HIGH: For dishwasher (97.3% OFF in train), the
     raw ratio * 2.0 = ~72, capped at 20 but still catastrophic.
     sqrt-based weighting needed.

IMPROVEMENT ROUND #2 — Changes Implemented
-------------------------------------------

  1. REPLACED DISHWASHER WITH FURNACE (config.py):
     Dishwasher has noisy, low-power signals unusable for NILM.
     Furnace (furnace1) has a clean bimodal distribution:
       - Idle/fan: 1-50W (76% of readings)
       - Heating active: 200W+ (24% of readings)
     This gives ~24% ON at 200W threshold — near-ideal class balance.

  2. REFINED ALL THRESHOLDS (config.py):
       - air1: 200W -> 300W (sits in clear gap between <50W and 500W+)
       - refrigerator1: 30W -> 50W (cleaner compressor-on separation)
       - furnace1: 200W (new, separates idle fan from active heating)

  3. SQRT-BASED CLASS WEIGHTING (training.py):
     Changed from pos_weight = (n_off/n_on) * factor to:
       pos_weight = sqrt(n_off/n_on) * factor, capped at 5.0
     This prevents extreme weights that cause model collapse.
     Example: old dishwasher weight was ~72 (capped 20), now furnace
     with 76/24 ratio gets sqrt(3.17)*1 = 1.78 — very reasonable.

  4. STATISTICAL FEATURES (dataset.py):
     Each window now has 5 appended features: mean, std, max, min,
     and slope (first-to-last gradient). This gives the model summary
     statistics about the window shape, helping distinguish between
     different aggregate power profiles. Total input: 60+5 = 65 dims.

  5. INCREASED MODEL CAPACITY (config.py):
     - MLP: [128,64] -> [256,128,64] (3 layers, more parameters)
     - LSTM: hidden 64 -> 128 (doubles recurrent capacity)
     - LSTM head: 32 -> 64 neurons (more capacity in output heads)
     Both models can now capture more complex patterns.

  6. LSTM ARCHITECTURE (lstm_model.py):
     Statistical features are now concatenated with the LSTM's last
     hidden state BEFORE the classification/regression heads, giving
     the heads both temporal and statistical information.

  7. REDUCED CLASS_WEIGHT_FACTOR (config.py):
     2.0 -> 1.0. Combined with sqrt-based weighting and focal loss,
     this prevents over-correction for minority class.
